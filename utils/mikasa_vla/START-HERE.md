# MIKASA CabinetRetrieval: датасет, dummy policy, обучение VLA

Что это: 1000 успешных эпизодов задачи `MikasaCabinetRetrieval-v0` («Take the cup out of the
open wall cabinet and set it down on the counter»), снятых в ManiSkill на **стоковом** Fetch с
камерами 224×224. Планирование велось на нашем роботе `ds_fetch`, а кадры и физика — реплей на
стоковом (`fetch_cam224`: тот же `fetch`, только размер камер наш). В самом роботе, с которого
сняты кадры, ничего нашего нет: URDF стоковый, пределы суставов стоковые. Это записано в
`meta/mikasa_format.json` и в `pool.env` сырого пула.

Подробности каждого шага — в `RUNNING-VLA.md` (в форке: `utils/mikasa_vla/RUNNING-VLA.md`).
Здесь — дорога от нуля до цифры.

## 0. Что скачивать

Для обучения — **только** `nurtayev-d/retrieval-try-1` (2.6 ГБ, LeRobot v2.1, 1000 эпизодов,
354 498 кадров, 10 Гц, все эпизоды успешные).

Сырой `nurtayev-d/retrieval-try-1-raw` (~30 ГиБ) для обучения не нужен: 97.6% его объёма — те
же кадры, только несжатые, а в LeRobot-версии они уже лежат в mp4. Он нужен, только если
понадобятся **состояния сцены** — позы объектов и всех сочленений кухни, которых в LeRobot-версии
нет.

```bash
export HF_HOME=/big/disk/hf          # иначе 2.6 ГБ уедут в ~/.cache и потеряются с контейнером
huggingface-cli download nurtayev-d/retrieval-try-1 --repo-type dataset \
    --local-dir $HF_HOME/lerobot/nurtayev-d/retrieval-try-1
```

Качать заранее не обязательно: `LeRobotDataset("nurtayev-d/retrieval-try-1")` скачает сам при
первом обращении, в тот же путь.

## 3. Dummy policy — первое, что запускать

Проверка **проводки**, а не модели: ни чекпойнта, ни openpi не нужно, политика работает в том же
процессе. Берёт картинки, проприо и текст, возвращает действия, они идут в `env.step`.

```bash
python utils/mikasa_vla/eval_policy.py --policy dummy \
       --seeds 9000-9001 --max-steps 40 --expect-image 224
```

Ожидаемый вывод:

```
env at 10 Hz control, 0.100 s a step
seed 9000: FAIL steps=40    seed 9001: FAIL steps=40
=== 0/2 ===
dummy policy: 12 inference calls, contract held;
  image (224, 224, 3), wrist (224, 224, 3), state (15,), prompt 73 chars
```

**`FAIL` здесь — успех.** Заглушка возвращает нули (или `--dummy-motion jitter`) и ничего не
решает намеренно. Проверяется договор: ровно четыре ключа `observation/image`,
`observation/wrist_image`, `observation/state`, `prompt`; обе картинки `uint8 (H, W, 3)`,
квадратные, одного размера и равные `--expect-image`; состояние `float32` шириной 15; промпт
непустой. Нарушение — исключение с именем ключа и тем, что пришло. Если вместо `contract held`
вылетело исключение, до обучения идти бессмысленно.

## 4. Адаптер в openpi

Датасет сам не говорит модели, как читать свои строки.

```bash
cp utils/mikasa_vla/openpi/mikasa_policy.py  <openpi>/src/openpi/policies/mikasa_policy.py
cd <openpi> && git apply --3way <клон>/utils/mikasa_vla/openpi/config.py.patch
```

`mikasa_policy.py`: головная камера → `base_0_rgb`, наручная → `left_wrist_0_rgb`, третий слот
модели заполнен нулями и **замаскирован** (камеры две, а не три), состояние 15 чисел как есть,
выход модели обрезан до 13 каналов. `config.py.patch` добавляет перепаковку ключей и два
конфига обучения; в обоих `repo_id="nurtayev-d/retrieval-try-1"`.

Если в openpi уже лежит старый блок MIKASA — его надо **заменить**, а не дописать рядом. Старые
копии встречаются с состоянием 29 и лишней камерой `observation/image2`; такое падает `KeyError`
на первом батче обучения, а не при импорте. Откат: openpi под git, `git checkout -- src/openpi`.

Проверка адаптера на настоящем кадре из датасета — **имя датасета позиционное, не `--repo`**:

```bash
python utils/mikasa_vla/openpi/check_adapter.py nurtayev-d/retrieval-try-1 --openpi <openpi>/src
```

## 5. Нормировочная статистика

```bash
cd <openpi> && uv run scripts/compute_norm_stats.py pi05_mikasa_retrieval
```

Мёртвых каналов в этом датасете нет ни одного, но **канал действий 8** (поворот головы) близок к

## 6. Обучение

```bash
cd <openpi> && uv run scripts/train.py pi05_mikasa_retrieval \
       --exp-name=retrieval_1000 --overwrite
```

| конфиг | что это | шагов | последний чекпойнт | память |
|---|---|---|---|---|
| `pi05_mikasa_retrieval` | **основной**: полное дообучение pi05, батч 64 | 30 000 | `…/29999` | карта класса A100/H100 (80 ГБ) или несколько |
| `pi05_mikasa_retrieval_low_mem` | LoRA на обеих половинах, батч 16 | 10 000 | `…/9999` | влезает в 23 ГБ (L4) |

Номер каталога чекпойнта — это номер шага, `num_train_steps - 1`. Чекпойнты пишутся каждые 1000
шагов (`save_interval`), кратные 5000 (`keep_period`) не удаляются — по ним и сравнивают.

Несколько карт: батч делится между ними и должен делиться **нацело**, иначе openpi падает с
`Batch size 64 must be divisible by the number of devices`. Модель шардится по FSDP:

```bash
uv run scripts/train.py pi05_mikasa_retrieval --exp-name=retrieval_1000 --overwrite \
       --fsdp-devices 4        # 4 карты, батч 64 = 16 на карту
```

`--batch-size`, `--num-train-steps`, `--save-interval`, `--keep-period` переопределяются из
командной строки. Датасет берётся по имени из конфига (`repo_id`), а не из аргументов.

LoRA-конфиг на большой карте брать не стоит, если цель — цифра: расписание скорости обучения
(косинус, прогрев 1000 шагов, спад на 30 000) рассчитано на полное дообучение с батчем 64, и
1000 эпизодов при нём проходятся примерно пять с половиной раз. LoRA остаётся для машины без
80 ГБ и для быстрой проверки, что цепочка едет.

## 7. Подать политику и оценить

```bash
# там, где чекпойнт (venv openpi):
uv run scripts/serve_policy.py policy:checkpoint \
       --policy.config=pi05_mikasa_retrieval --policy.dir=<checkpoints>/retrieval_1000/29999

# там, где mani_skill:
python utils/mikasa_vla/eval_policy.py --seeds 9000-9099 --control-freq 10 \
       --video-dir /tmp/eval --expect-image 224
```

**Оценочный набор зафиксирован: сиды 9000–9099, сто штук.** Они не пересекаются с обучающими:
в датасете заняты 1100–2109 (точный список — колонка `seed` в `meta/mikasa_episodes.csv`).
Брать сиды из обучающего набора — значит получить цифру, которая ничего не значит.

Потолок на этом наборе измерен: **оракул (наш планировщик) решает 100 из 100**, ни одного
промаха, ни одного эпизода без плана, ни одного обрыва по времени (замерено 2026-09-12,
`evaluate_planner`, 10 Гц, `pd_joint_delta_pos`). То есть все сто сцен разрешимы, и любой
результат политики ниже ста — это её недоработка, а не невезение с расстановкой.

## 8. Ловушки, каждая с ценой

| ловушка | чем оборачивается |
|---|---|
| **Частота.** Умолчание ManiSkill — 20 Гц, все данные записаны на 10 | политика за шаг проходит вдвое меньше, чем училась, и выглядит бестолковой. Ошибки при этом нет ни одной. `--control-freq 10` обязателен |
| **Седьмой канал действий** — не дельта, а **абсолютное** раскрытие захвата (−0.01…0.05 м); 11 000 шагов из 354 498 (3.1%) — промежуточные значения | политика, трактующая его как дельту, не разожмёт схват |
| **Порядок состояния ≠ порядок действий**: `qpos` как есть, `head_pan` стоит **между** торсом и `shoulder_pan`, последние два столбца — пальцы в порядке объявления в URDF | обучение на перепутанных суставах, молча |
| **Размер камер** 224 у обеих | менять размер — значит пересобирать датасет: среда берёт размер у робота |
| **Старый адаптер** (состояние 29, `image2`) | `KeyError` на первом батче |
| **`HF_HOME` не задан** | 2.6 ГБ уедут на диск контейнера и потеряются |
| **Сиды оценки из обучающего набора** | цифра успеха, которая ничего не значит |

## 9. Что считать результатом

`eval_policy` печатает по сиду `SUCCESS`/`FAIL` и итог вида `=== 37/100 ===`. Сравнивать надо с
оракулом на **тех же** сидах: на наборе 9000–9099 он даёт 100/100, это потолок, а не цель.
Видео из `--video-dir` нужно, чтобы понять, **как** политика проваливается: не доезжает,
промахивается схватом, роняет чашку.

Ещё одна проверка, которую стоит сделать один раз: политика, обученная на этих данных, не
обязана оставаться в том же роботе. Кадры и физика датасета сняты на немодифицированном Fetch,
так что перенос на стоковый робот уже заложен в данные, а не проверяется задним числом.

## 10. Что внутри датасета

```
data/chunk-000/episode_000000.parquet … episode_000999.parquet   действия, состояние, время (51 МБ)
videos/chunk-000/image/episode_*.mp4          головная камера, поворачивается с head_pan/head_tilt
videos/chunk-000/wrist_image/episode_*.mp4    наручная камера
                                              обе 224×224, h264 crf 23, fov 2.0 рад, вдвоём 2.5 ГБ
meta/info.json           признаки и счётчики
meta/episodes.jsonl      номер, задача, длина эпизода
meta/episodes_stats.jsonl статистика признаков по эпизодам
meta/tasks.jsonl         единственный текст задачи
meta/mikasa_format.json  карточка формата: режим, частоты, робот, таблица 13 каналов, порядок
                         15 чисел состояния, происхождение обоих этапов записи
meta/mikasa_episodes.csv 1000 строк: episode_index, seed, env_id, steps, duration_s, success,
                         from_index, to_index, instruction_idx, file
```

Действий 13, это собственные действия среды в режиме `pd_joint_delta_pos`, все каналы уже
нормированы и подаются в `env.step` напрямую. Каналы 0–6 — дельты суставов руки (±0.1 рад за
шаг), 7 — абсолютное раскрытие захвата, 8–10 — дельты `head_pan`, `head_tilt`, `torso_lift`,
11–12 — линейная и угловая скорость базы.

Состояние — `obs['agent']['qpos']` как есть, 15 чисел: первые три — положение базы в мире,
затем `torso_lift`, затем `head_pan`, и только потом суставы руки; последние два — правый и
левый пальцы. **Порядок состояния не совпадает с порядком действий.**
