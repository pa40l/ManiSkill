# MIKASA: как получить записи траекторий

Ветка несёт три задачи бенчмарка памяти и всё, что нужно, чтобы записать по ним демонстрации
оракула в формате из записки «MIKASA-2: перевод сбора данных на `pd_joint_delta_pos`»
(2026-09-08). Ниже — путь от клона репозитория до датасета LeRobot, каждый шаг проверен на
чистом клоне.

Всё, что относится к MIKASA, лежит в трёх местах, как просит `AGENTS.md` форка:

| где | что |
|---|---|
| `my_scenes/` | сцены задач: `season_dish.py`, `cabinet_search.py`, `cabinet_retrieval.py` |
| `planners/` | оракулы: `season_dish_planner.py`, `cabinet_search_planner.py`, `cabinet_retrieval_planner.py` |
| `utils/mikasa/` | то, что нужно, чтобы ЗАПУСТИТЬ задачу: робот `mikasa_ds_fetch`, сцены-основы, утилиты |
| `utils/mikasa_oracle/` | то, что нужно, чтобы ПОЛУЧИТЬ ЧИСЛА: солвер (mplib), протокол оракула, свип `evaluate_planner` |
| `utils/mikasa_vla/` | инструменты сбора данных: эта инструкция, проверка формата, повтор в rgb, конвертер в LeRobot |

Разделение половин не косметическое: политика на инференсе грузит только `utils/mikasa` — без
mplib и без оракулов.

## 1. Установка

```bash
git clone -b mikasa-record https://github.com/pa40l/ManiSkill.git
cd ManiSkill
python -m venv .venv && . .venv/bin/activate     # Python 3.11
pip install -e .                                  # тянет torch, sapien, mplib 0.2.1, gymnasium, h5py …
pip install toppra==0.6.10                        # тайминг траекторий солвера, единственное сверх setup.py
python -m mani_skill.utils.download_asset RoboCasa   # ~8 ГБ в ~/.maniskill
```

Версии, на которых всё измерено: Python 3.11.13, `mani_skill` 3.0.0b22 (этот форк),
`sapien` 3.0.3, `mplib` 0.2.1, `toppra` 0.6.10, `numpy` 1.26.4, `gymnasium` 0.29.1,
`torch` 2.14.0, `h5py` 3.16.0.

Проверка, что среда собралась (регистрация задач и один шаг):

```bash
python -c "
import mani_skill, gymnasium as gym
env = gym.make('MikasaCabinetRetrieval-v0', obs_mode='state',
               control_mode='pd_joint_delta_pos', num_envs=1,
               sim_backend='physx_cpu', robot_uids='mikasa_ds_fetch')
obs, _ = env.reset(seed=1100)
print('ok', env.unwrapped.get_language_instruction()[0][:60])
env.close()"
```

## 2. Один эпизод

```bash
python -m utils.mikasa_oracle.evaluate_planner \
  -s MikasaCabinetRetrieval-v0 -p cabinet_retrieval_planner \
  -n 1 --start-seed 1100 --obs-mode state --scene-idx 0 \
  --control-mode pd_joint_delta_pos --control-freq 10 \
  --traj-dir /data/mikasa/state/retrieval/seed_1100
```

Пишет `<traj-dir>/<штамп>.h5` + `.json` — то есть каталог `--traj-dir` задаёте сами, по одному
на сид (так делают пулы ниже; инструменты принимают и плоскую раскладку). Строка `EP 1/1 seed=1100 SUCCESS …`
означает, что предикат задачи защёлкнулся.

Что означают ключевые флаги:

* `--control-mode pd_joint_delta_pos` — нативный формат из записки: 13 каналов, каждый в
  `[-1, 1]`, никакой конвертации после записи;
* `--control-freq 10` — частота управления среды, она же частота данных. Действие — это дельта
  за ОДИН шаг управления, поэтому частота данных обязана совпадать с той, на которой действия
  применялись. Планы оракула тайминг берут из `control_timestep`, поэтому сами перестраиваются;
* `--scene-idx 0` — кухня 102, на ней всё измерено; без флага RoboCasa разыгрывает кухню из 120;
* `--obs-mode state` — без картинок (быстро). Для датасета нужны картинки — см. §3.

Сид воспроизводится ровно один раз: `env.reset(seed=s)` на построенной среде. Никогда не
`options=dict(reconfigure=True)` — переконфигурация заново разыгрывает столешницу станции, и тот
же сид даёт другую раскладку.

## 3. Пул записей: два пути

**Путь А — прямая запись с картинками.** Один процесс на сид, `--obs-mode rgb`:

```bash
python -m utils.mikasa_oracle.evaluate_planner \
  -s MikasaSeasonDish-v0 -p season_dish_planner \
  -n 1 --start-seed 3800 --obs-mode rgb --scene-idx 0 \
  --control-mode pd_joint_delta_pos --control-freq 10 \
  --traj-dir /data/mikasa/rgb/season_dish/seed_3800
```

Пул — это тот же вызов по одному процессу на сид; параллелить лучше через `xargs -P`, а не
`-n 200` в одном процессе: один упавший эпизод тогда не уносит остальные.

**Путь Б — записать действия на state, потом прокрутить их в rgb-среде** (ваша подсказка от
2026-09-10). Сначала пул на `--obs-mode state`, затем:

```bash
python utils/mikasa_vla/replay_to_rgb.py /data/mikasa/state/retrieval /data/mikasa/rgb/retrieval
```

Каталог на входе — тот, внутри которого лежат `seed_*/…h5` (или сами `*.h5`).

Повтор точный, а не приблизительный: записанные действия подаются в свежую среду того же сида и
той же частоты, и эпизод записывается, только если вернулись и флаг успеха, и конечный `qpos`
(на одной машине расхождение 0.0).

Что выбрать (измерено 2026-09-10, Retrieval, сид 1100, 10 Гц, одно ядро):

| путь | стена | пик памяти |
|---|---|---|
| план + шаги, `--obs-mode state` | 5.6 с | 1.34 ГБ |
| план + шаги, `--obs-mode rgb` (путь А) | 15.2 с | 1.99 ГБ |
| повтор state → rgb (вторая половина пути Б) | 8.4 с | 2.6 ГБ |

По суммарному времени пути равны (5.6 + 8.4 против 15.2). Путь Б выигрывает в другом: планирование
оплачено один раз, поэтому набор камер, их разрешение и режим наблюдения становятся решением,
принимаемым ПОСЛЕ записи (10.09 у робота сменились камеры, и 100 записанных эпизодов потеряли
кадры, сохранив действия), а провалившиеся сиды не стоят рендера вовсе.

Параллельность и объёмы: rgb-процесс держит кадры в памяти до сброса в h5 — при 62 ГБ cgroup
безопасно 10 процессов; state-процессов помещается больше. Эпизод Retrieval ≈ 45 МБ,
CabinetSearch в 3–6 раз крупнее (эпизоды до 2500 шагов при 10 Гц).

## 4. Проверка формата — та, что описана в записке

```bash
python utils/mikasa_vla/check_recordings.py /data/mikasa/rgb/retrieval --limit 5
```

Проверяются ровно четыре вещи из записки, плюс повтор:

1. массив действий имеет форму `(T, 13)` и все значения в `[-1, 1]` — забытый абсолютный канал
   виден здесь как значение больше единицы;
2. `obs/agent/qpos` имеет форму `(T+1, 15)` — состояние это только qpos, ничего больше;
3. печатается доля шагов, где канал руки упёрся в ограничение (`|a| > 0.999`); на текущем дереве
   она равна нулю на всех трёх задачах при 10 Гц;
4. записанные действия подаются обратно в свежую среду того же сида — успех обязан вернуться, а
   конечный `qpos` совпасть (допуск `--tol`, по умолчанию 5 мм; на одной машине 0.0).

Вывод вида `OK … arm_clip=0.0 … replay_success=True qpos_err=0.0 stock_fetch=ok` и две
итоговые строки: сколько записей прошли проверку и сколько из них воспроизводятся на
НЕМОДИФИЦИРОВАННОМ Fetch. Второе — про пределы суставов: поза за пределом сустава на стоковом
роботе просто обрежется, и эпизод разойдётся. С 2026-09-10 у роликовых суставов в нашем URDF
стоковые ±3.141, так что расхождение остаётся только по виртуальному повороту базы (у нас ±50
рад против ±6.28, иначе солвер не доводит развороты); `--stock-strict` превращает выход за
пределы в ошибку записи.

## 5. Датасет LeRobot

```bash
python utils/mikasa_vla/h5_to_lerobot.py --raw /data/mikasa/rgb/retrieval --repo mikasa/retrieval_10hz
```

Камеры пишутся в MP4 (`dtype: "video"` — каталог `videos/` рядом с `data/`), как и в
конвертере MIKASA-Robo. Флаг `--frames` кладёт вместо этого PNG-кадры (их `--no-videos`).
На пяти эпизодах Retrieval (2897 кадров) это 29 МБ против 235 МБ; `LeRobotDataset` в обоих
случаях отдаёт один и тот же тензор `(3, 256, 256)` float32 в `[0, 1]`.

Конвертер последовательный: он читает эпизод, пишет кадры, зовёт ffmpeg и переходит к
следующему, и больше полутора ядер занять не может. На тысяче эпизодов это около двух с
половиной часов. Если ядра есть, пул режется на срезы, на каждый запускается свой конвертер в
свой `--repo`, и результаты сшиваются — 1000 эпизодов Retrieval так собрались за 35 минут
вместо 2.5 часов:

```bash
python utils/mikasa_vla/merge_lerobot_shards.py --out mikasa/retrieval_10hz --expect 1000 \
    --shards mikasa/shard0 mikasa/shard1 ... mikasa/shard6
python utils/mikasa_vla/h5_to_lerobot.py --raw <объединённый пул> --repo mikasa/retrieval_10hz \
    --card-only --vcodec h264 --crf 23
```

Сшивка перенумеровывает `episode_index`, сквозной `index` и `task_index` (через тексты задач, а
не номера) и в parquet, и в `episodes_stats.jsonl`; видео переносятся жёсткой ссылкой. Она
откажется сшивать шард, в котором ещё работает конвертер, — такой шард выглядит просто меньшим
датасетом, и все его внутренние проверки сходятся, поэтому `--expect` обязателен. Второй шаг
пишет карточку и заодно сверяет датасет с пулом эпизод за эпизодом: если чего-то не хватает,
карточка не будет написана.

Частота датасета не задаётся руками: она читается из записи (`sim_config.control_freq`), потому
что одно записанное действие — это один шаг управления. Рядом с датасетом кладётся карточка
`meta/mikasa_format.json` — то, чего в метаданных LeRobot нет вовсе (её конвертер не переносит
даже `control_mode`): режим управления, частоты `control_freq_hz` и `sim_freq_hz` с числом
физических подшагов на действие, робот и URDF, чем закодированы картинки, таблица 13 каналов с
границами, порядок 15 чисел состояния, тексты задач, коммит, и списки `inactive_channels` /
`near_inactive_channels` — каналы с нулевой (или меньше 1e-3) дисперсией, на std которых делить
при нормализации нельзя. Обе частоты читаются из записи, а не берутся константой.

## 6. Что внутри данных

* **Действия, 13 каналов, все в `[-1, 1]`**: рука 7 дельт (±0.1 рад за шаг), схват 1 абсолютный
  (0…0.05 м), тело 3 дельты (`head_pan`, `head_tilt`, `torso_lift`), база 2 скорости (вперёд
  ±1 м/с, поворот ±3.14 рад/с). База дифференциальная, боком не ездит.
* **Состояние, 15 чисел** — `obs["agent"]["qpos"]` как есть, в порядке суставов симулятора
  (первые три — x, y, yaw базы; `head_pan` стоит между торсом и плечом, это не порядок действий).
* **Камеры** — как у настоящего Fetch: `fetch_head` 256×256 на голове (поворачивается вместе с
  ней) и `fetch_hand` 128×128 на кисти.
* **Текст задачи** — `env.unwrapped.get_language_instruction()`; у каждой задачи три
  формулировки, они называют дело, но не ответ.

## 7. Что уже измерено на этом дереве

Оракулы, режим `pd_joint_delta_pos`, по 200 сидов на задачу: SeasonDish 200/200 (сиды 3800–3999),
CabinetSearch 200/200 (2300–2499), CabinetRetrieval 200/200 (1100–1299). Это на 20 Гц; на 10 Гц
проверены по три сида каждой задачи — успех и нулевая доля клипа руки.

Оракулы ходят прямыми планами: линия в пространстве суставов или винт; RRT остался только на
подходе к захвату приправы (примерно треть эпизодов SeasonDish). Это видно в логе как
`plan=line` / `plan=screw` / `plan=rrt`.
