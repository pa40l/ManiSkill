# MIKASA: как обучить и проверить VLA на записанном датасете

Продолжение `recording-guide.md`. Тот доводит до датасета LeRobot; этот — от датасета до
обученной политики, которая едет в ту же среду, в которой собирались данные. Каждая команда
ниже запускалась; числа — замеренные, не взятые из документации.

Нужно до старта: датасет (опубликован как `nurtayev-d/retrieval-try-1` — 1000 эпизодов
Retrieval, 354 498 кадров, 10 Гц; локально тот же датасет зовётся
`mikasa/retrieval_stock224_h264_crf23`), видеокарта
NVIDIA и склонированный openpi. Мы работаем на L4 с 23 ГБ.

## 1. Перенести адаптер в openpi

Датасет сам по себе не говорит модели, как читать его строки. Это делают два файла из
`utils/mikasa_vla/openpi/` (в приватном дереве — `tools/vla/openpi/`):

| файл | что делает |
|---|---|
| `mikasa_policy.py` | головная камера → `base_0_rgb`, наручная → `left_wrist_0_rgb`, третий слот модели заполнен нулями и **замаскирован** (у робота двух камер, а не трёх), состояние 15 чисел как есть, выход модели обрезан до 13 каналов |
| `config.py.patch` | добавляет в `openpi/training/config.py` перепаковку ключей и два конфига обучения |

```bash
cp utils/mikasa_vla/openpi/mikasa_policy.py  <openpi>/src/openpi/policies/mikasa_policy.py
cd <openpi> && git apply --3way <репо>/utils/mikasa_vla/openpi/config.py.patch
```

**Если в живом openpi уже лежит блок MIKASA — его надо заменить, а не дописать рядом.** Старые
копии встречаются с состоянием 29 и лишней камерой `observation/image2`; обучение на таком
падает `KeyError` на первом батче, а не при импорте. Откат всегда есть: openpi под git,
`git checkout -- src/openpi` возвращает как было.

## 2. Две дешёвые проверки до обучения

Обе занимают минуты и ловят то, что иначе проявится через час обучения.

**Адаптер против настоящего кадра.** Собственный пример адаптера проверить его не может: он
написан той же рукой и согласован с ним по построению.

```bash
python utils/mikasa_vla/openpi/check_adapter.py nurtayev-d/retrieval-try-1
```

Имя датасета здесь позиционное, а не `--repo`. Оно же стоит в обоих конфигах обучения
(`repo_id`), так что менять его нужно в одном месте, а не в командной строке. Если датасет уже
лежит под `$HF_HOME/lerobot/nurtayev-d/retrieval-try-1`, он берётся с диска; если нет —
скачивается с Hugging Face по этому же имени.

**Петля оценки против политики-заглушки.** Проверяется договор между наблюдением и средой:
те же ключи, что в датасете, обе картинки uint8 и квадратные, состояние float32 шириной 15,
инструкция непустая. Заглушка возвращает нули, поэтому эпизоды провалятся — и это правильный
результат: проверяется проводка, а не поведение.

```bash
python utils/mikasa_vla/eval_policy.py --policy dummy --seeds 9000-9001 \
       --max-steps 40 --expect-image 224
# ожидается: "contract held; image (224, 224, 3), wrist (224, 224, 3), state (15,)"
```

## 3. Нормировочная статистика

Считается один раз на конфиг и кладётся в assets openpi:

```bash
cd <openpi> && uv run scripts/compute_norm_stats.py pi05_mikasa_retrieval_low_mem
```

Осторожно с каналами, у которых дисперсия почти нулевая: карточка датасета называет их в
`inactive_channels`, `near_inactive_channels` и `near_constant_state_columns`. Делить на их
разброс нельзя — нормировка по MIN_MAX или квантилям превращает численный шум в команду во
весь диапазон. У Retrieval это канал 8 (поворот головы) и колонка состояния 4.

## 4. Обучение

```bash
cd <openpi> && uv run scripts/train.py pi05_mikasa_retrieval \
       --exp-name=retrieval_1000 --overwrite
```

| конфиг | что это | шагов | последний чекпойнт | память |
|---|---|---|---|---|
| `pi05_mikasa_retrieval` | **основной**: полное дообучение pi05, батч 64 | 30 000 | `…/29999` | нужна карта класса A100/H100 (80 ГБ) или несколько |
| `pi05_mikasa_retrieval_low_mem` | LoRA на обеих половинах, батч 16 | 10 000 | `…/9999` | влезает в 23 ГБ (L4) |

Номер каталога чекпойнта — это номер шага, то есть `num_train_steps - 1`; брать его надо из
конфига, а не из чужого примера. Чекпойнты пишутся каждые `save_interval` (1000) шагов, и те,
что кратны `keep_period` (5000), не удаляются — по ним и сравнивают.

Если карта одна и большая — ничего менять не нужно. Если карт несколько, батч делится между
ними, и openpi требует, чтобы он **нацело** делился на число устройств (иначе падает с
`Batch size 64 must be divisible by the number of devices`). Модель шардится по FSDP:

```bash
uv run scripts/train.py pi05_mikasa_retrieval --exp-name=retrieval_1000 --overwrite \
       --fsdp-devices 4        # 4 карты; батч 64 = 16 на карту
```

`--batch-size`, `--num-train-steps`, `--save-interval` и `--keep-period` тоже переопределяются
из командной строки, если хочется прогона длиннее или чаще сохраняться. Датасет берётся по
имени из конфига (`repo_id`) — если собрали свой, правится там, а не в аргументах.

Стоит ли брать LoRA-конфиг на большой карте: нет, если цель — цифра. Полное дообучение на
батче 64 — это то, на что рассчитано расписание скорости обучения (косинус с прогревом 1000
шагов и спадом на 30 000), и 1000 эпизодов при нём проходятся примерно пять с половиной раз.
LoRA-конфиг остаётся для машины, где 80 ГБ нет, и для быстрой проверки, что вся цепочка едет.

## 5. Подать политику и оценить

```bash
# на машине с чекпойнтом, в venv openpi (номер каталога = num_train_steps - 1):
uv run scripts/serve_policy.py policy:checkpoint \
       --policy.config=pi05_mikasa_retrieval --policy.dir=<checkpoints>/retrieval_1000/29999

# в venv с mani_skill:
python utils/mikasa_vla/eval_policy.py --seeds 9000-9099 --control-freq 10 \
       --video-dir /tmp/eval --expect-image 224
```

**Сиды оценки не должны встречаться в датасете.** Какие в нём есть — написано в
`meta/mikasa_episodes.csv` рядом с датасетом, столбец `seed`. У нас записаны 1100–2109, поэтому
на оценку берутся 9000 и выше.

## 6. Ловушки, каждая с ценой

| ловушка | чем оборачивается |
|---|---|
| **Частота.** Умолчание ManiSkill — 20 Гц, все наши данные записаны на 10 | политика проходит за шаг вдвое меньше, чем училась, и выглядит бестолковой. Ошибки при этом нет ни одной. `eval_policy` требует `--control-freq`, по умолчанию 10 |
| **Размер камер.** Обучение и оценка обязаны идти на одном размере | в датасете 224 у обеих камер; среда берёт их у робота, так что менять размер значит пересобирать датасет |
| **Старый адаптер** с состоянием 29 и `image2` | `KeyError` на первом батче обучения |
| **`HF_HOME`** | без него lerobot положит датасет в `~/.cache/huggingface`, то есть на диск контейнера, и потеряет при его пересоздании |
| **Каналы с нулевой дисперсией** | `nan` в нормировке или шум, растянутый на весь диапазон |
| **Сиды оценки из обучающего набора** | цифра успеха, которая ничего не значит |

## 7. Что считать результатом

`eval_policy` печатает по сиду `SUCCESS` или `FAIL` и итог вида `=== 37/100 ===`. Сравнивать его
имеет смысл с оракулом на тех же сидах. Оценочный набор зафиксирован — сиды **9000–9099**, и
оракул на нём даёт **100 из 100** (замерено 2026-09-12: ни промаха, ни эпизода без плана, ни
обрыва по времени). Это потолок, а не цель, и он же говорит, что все сто сцен разрешимы. Видео из `--video-dir` снимается камерой человека и нужно, чтобы понять **как** политика
проваливается: не доезжает, промахивается схватом, роняет.

Отдельно стоит проверить перенос на немодифицированного Fetch: наши записи исполняются на нём
199 раз из 200 (расхождение по суставам 0.0013 рад в медиане), так что политика, обученная на
этих данных, не обязана оставаться в том же роботе.
